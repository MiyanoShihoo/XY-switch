> **本文档的读者**是接手实现这件事的人（可能是未来的你，也可能是我）。它把设计落到
> XY Switch 的**真实代码位置**上，而不是泛泛而谈。

## 一、核心判断：先做被动审计，不要先做主动探针

我做那套检测框架时，把一条局限写在 `docs/05` 的第一位，并且承认它从客户端**原则上
解决不了**：

> 探针流量和业务流量是可以区分的。中转商只要识别出「这是在被检测」，就可以把探针
> 请求转给真模型、把业务请求转给假模型。

我自己写的那个假中转站就是靠匹配提示词特征认出探针的 —— 它能验证检测逻辑对不对，
但验证不了能不能对抗一个会作弊的对手。

**XY Switch 不存在这个问题。** 它处在转发位置上，看到的就是真实业务流量，没有可被
区分的「探针」。这不是一个功能改进，这是把那条根本局限直接拿掉。

所以实施顺序是反的：**先把被动能拿到的东西全部拿到，主动探针留到最后**。被动部分
的三个性质决定了这个优先级 —— 零额外成本（反正要转发）、不可被规避（它就是正常
使用）、样本量随使用自然增长。

## 二、现状盘点：已经有什么

好消息是基础设施基本就位，P0 的改动比想象的小。

**`request_events` 表已经在记这些**（`database.rs:1187` 建表，`database.rs:411-437`
迁移）：

```
provider_id, route, status_code, success, latency_ms, retry_count,
error_kind, created_at, model, input_tokens, output_tokens,
cache_creation_tokens, cache_read_tokens, cost, price_source, price_version
```

**写入是「先插后补」两段式**，这个结构恰好适合挂检测：

| 位置 | 做什么 | 现状 |
|---|---|---|
| `proxy.rs:715` `record_request()` | 插入 event 拿到 `event_id` | token 字段全填 `None` |
| `proxy.rs:862` `persist_non_stream_usage()` | 非流式回填 | 这里拿得到**完整响应 body** |
| `streaming.rs:1049` `if !usage_recorded` | 流式结束回填 | 这里是逐帧循环的终点 |
| `database.rs:760` `update_request_usage()` | 执行 UPDATE | 结构体是 `RequestUsage`（`database.rs:270`） |

**迁移机制是幂等的**（`database.rs:411`）：`PRAGMA table_info` 读现有列，缺哪个就
`ALTER TABLE ADD COLUMN`。加字段照这个模式走，不会破坏旧库，重复运行也安全。

**依赖里已经有 `sha2`**，所以指纹文件哈希不用新增依赖。

### 三个现状缺口

**① 可见输出字节数没有被记录。** `streaming.rs` 的 `Context`（第 45-66 行）有
`input_tokens` / `output_tokens`，但**没有累积可见文本的字节数**。文本是作为
`Delta::Text(String)` 事件流过的（产生点在第 199/268/413/428/487 行，消费点在
534/611/717/848 行），流过就扔了。

这是最可惜的一处 —— 它只需要几行就能产出 **Proof 级硬证据**（见 P0）。

**② 记的是上游自报的 model，但请求的原始 model 被覆盖丢失了。**

这一点我第一遍读代码时判断反了，核对后是这样：

- 流式路径：`Context::new(model)` 用请求的 model 初始化，但解析上游响应时
  **只要上游给了 model 就覆盖掉它** —— `streaming.rs:168-169`（Chat）、
  `260-262`（Responses）、`398-400`（Anthropic）三处都是
  `context.model = model.to_string();`
- 非流式路径：`extract_non_stream_usage()`（`proxy.rs:805-812`）同样优先取
  `body["model"]` 或 `body["modelVersion"]`，请求的 model 只作 `unwrap_or` 的兜底

所以**数据库里记的 model 已经是上游自报的那个值** —— 这对检测来说是好事，省了一步。
而且 `context.model` 随后还会渲染给客户端（`streaming.rs:522/555/607/681/819`），
也就是说上游老实自报 `cheap-model-v0` 的话，用户的客户端其实**看得到**。

真正的缺口是：**请求的原始 model 在覆盖后就没了**，所以无法做比对。要让
`inv.model_mismatch` 可用，得把原始值单独留一份（见 P0 的改动清单）。

顺便说清这条信号的分量：model 字段是**最容易伪造**的信号 —— 上游只要把自报名改成
请求的那个名字就完全看不出来。所以它值得记录（成本几乎为零），但权重必须压低，
不能单独定罪。真正难伪造的是 P1 的流式切分指纹。

**③ `total_tokens` 和 `reasoning_tokens` 没记。** 前者用于 usage 自洽检查，后者是
推理模型的必要混淆因素 —— 没有它会把 o 系、思考模式的模型全部误判成虚报用量。

**④ 请求的 `max_tokens` 传不到回填点。** `adapters.rs:258/384/570` 在处理请求时读过
它，但没带进 `Context`。`streaming.rs` 里出现的那三次 `max_tokens`
（第 442/577/794 行）**全是 finish_reason 的取值**，不是请求参数。所以
`inv.max_tokens_violated` 这条检查需要额外把请求参数带下来 —— 它是四条里唯一需要
改数据流的，建议放到最后做。

## 三、先做这一件：把上游自报的 model 显示出来

在进入 P0 之前，有一个**半天就能做完、而且直接回答「真实模型是谁」**的改动。

上面缺口②里说了：数据库 `model` 列存的已经是**上游自报的值**。也就是说这个信息
XY Switch 其实一直在记，只是从来没在界面上跟「你请求的是什么」并排显示过。

要做的只有三件事：

1. 迁移里加 `requested_model TEXT`（见 P0 改动清单第 1 条）
2. 两个回填点各多填一个字段：流式在 `streaming.rs:1049` 那段，非流式在
   `extract_non_stream_usage()` —— 请求的 model 本来就是它的 `fallback_model` 参数
3. 用量列表里加一列，两个值不同时标出来

- `className` 全是语义类（`cc-data-table`、`model-chip-table`、`status-pill`），
  不是原子类

**深色主题必须适配。** `src/styles/` 下有 **91 处 `[data-theme="dark"]`** 规则，
主题切换在 `SettingsView.tsx:276-281`（light / dark / system 三档）。

`log.model` —— 按第二节缺口②，**它显示的已经是上游自报的值**。所以要做的不是
「凭空加一列」，而是**把请求的 model 并排放上去做对比**。

> **加列时别忘了空状态的 `colSpan`。** logs 表格的空状态在

**三档显示可以照现有模式扩展，不用发明新东西。** 表格里已经有这套：

所以第三节那三档直接复用 `status-pill`：一致用 `status-ok`（已有），
不一致和无法判断各加一个修饰类，照 `status-fail` 的写法在 `usage.css` 里补。
图标从 `lucide-react` 取（表格里已经在用 `CheckCircle2` / `XCircle`）。

| 硬证据 / 危险 | `--xy-danger`、`--xy-danger-soft`、`--xy-danger-border` |

> 整个 `usage.css` 里有 32 处硬编码颜色、91 处 `var(--xy-*)`，两种风格混用。
>

> （和邻居一致，但同样缺深色适配），或者**用 token 写并顺手把 ok/fail 也改掉**
> （更好，但动了现有代码）。UI 重构时建议走后者，因为深色主题下硬编码的
> `#16a34a` 在深色背景上对比度本来就不够。

**前端有测试，UI 改动应该带上。** `src/` 下有 **12 个 vitest 测试文件**
（`provider-validation.test.ts` 这类），`npm test` 就是 `vitest run`。三档判定
是纯函数（给定请求 model 和上游 model，返回三档之一），很适合单独测 ——
特别是「上游未自报时必须判无法判断、不能判一致」那一条。

界面上长这样就够了：

```
模型            请求 gpt-4o → 上游自报 gpt-4o            ✓
模型            请求 gpt-4o → 上游自报 cheap-model-v0    ⚠ 不一致
模型            请求 gpt-4o → 上游未自报                  — 无法判断
```

**三档，不是两档。** 上游不返回 model 字段时是「无法判断」，不能算「一致」——
把没测到的说成没问题，是这类工具最常见也最有害的失败模式。

必须同时告诉用户这个信号的分量，否则会产生错误的确信：**model 字段是最容易伪造的
信号**，上游只要把自报名改成请求的那个名字就完全看不出来。所以「一致」几乎不说明
任何事情，而「不一致」是实打实的 —— 这个不对称性要让用户看见。

它的价值在于成本几乎为零而上限不低：真有中转商懒得改这个字段，那就直接抓到了。
真正难伪造的在 P1。

## 四、阶段 P0：被动不变量 —— 四类硬证据

这一阶段的全部价值在于：**产出的是 Proof 级结论，不依赖先验、不依赖权重、不依赖
任何参照物**，而且规避它等于「不作恶」。

### 要检测的四条

| 检查 | 判据 | 为什么不存在无辜解释 |
|---|---|---|
| `inv.byte_bound` | `可见输出 token 数 > 输出文本 UTF-8 字节数 + 余量` | 任何 BPE/SentencePiece 的普通 token 解码后至少 1 字节（字节回退 token 恰好 1 字节），所以 token 数 ≤ 字节数恒成立 |
| `inv.usage_selfcontradictory` | `input + output ≠ total`（上游给了 total 时） | 算术矛盾 |
| `inv.model_mismatch` | 上游自报 model ≠ 请求 model，且不在别名表里 | 它自己说的（但**极易伪造**，权重要压低） |
| `inv.max_tokens_violated` | 输出 token 数 > 请求的 `max_tokens` | 协议违约。**需要先把请求参数带到回填点**，见缺口④ |

前三条只在 `streaming.rs` / `proxy.rs` 本地加字段，不需要跨模块传参。
`max_tokens_violated` 要把请求参数从 `adapters.rs` 一路带到回填点，是唯一动数据流的，
放最后。

第一条是最硬的，也是**最能抓到虚报用量**的。但它有三个必须扣除的混淆因素，少扣一个
就会冤枉诚实渠道：

1. **推理 token**：o 系模型的 `completion_tokens` 含隐藏思考，而那些 token 不产生
   可见文本。必须减去上游上报的 `reasoning_tokens`。
2. **工具调用字节**：函数名和 JSON 参数也计费但不在可见文本里。`Context` 已经有
   `tool_arguments: Vec<String>` 和 `tool_names`，把它们的字节数算进来。
3. **特殊 token 余量**：`<|im_end|>` 这类解码后是 0 可见字节。留 4 个 token 的余量。

> **扣不干净就不要下结论。** 参照实现里的处理方式是：没有 `reasoning_tokens` 字段
> 又无法确认模型是否开了思考模式时，**直接跳过这条检查**并登记一个效力缺口，而不是
> 带着未扣除的混淆去指控。宁可不测，不可冤枉。

```rust
    requested_model: String,       // 新增：保存请求的原始 model，不被上游覆盖
    visible_output_bytes: u64,     // 新增：byte_bound 的核心
    text_delta_count: u64,         // 新增：文本增量帧数（P1 要用）
    reasoning_tokens: u64,         // 新增：各协议解析分支里顺手填
    total_tokens: Option<u64>,     // 新增：上游给了就记，用于自洽检查
}
```

`requested_model` 在 `Context::new()` 里初始化成传进来的 model，然后
**那三处 `context.model = model.to_string();`（168/261/399 行）保持原样不动** ——
它们让 `context.model` 变成上游自报的值，这是现有的透传行为，改了会影响客户端。
我们只是额外留一份原始值。

文本字节的累加点：不要去改那四个 `render_*` 函数（容易漏一个），在 delta 进入
分发之前统一拦一次：

```rust
// ⚠ 未经 cargo check 的示意代码，字段名/借用需按实际代码调整
// 示意：在 match state.client { ... render_*(delta, ...) } 之前
if let Delta::Text(text) = &delta {
    state.context.visible_output_bytes += text.len() as u64;
    state.context.text_delta_count += 1;
}
```

> `String::len()` 在 Rust 里返回的**就是 UTF-8 字节数**，不是字符数 —— 这正好是
> `byte_bound` 需要的量，不要改成 `chars().count()`。

工具调用字节不用新开字段：`Context` 已经有 `tool_arguments: Vec<String>` 和
`tool_names: Vec<Option<String>>`，在回填时现算它们的字节和就行。

**4) 流式回填**（`streaming.rs:1049` 那段 `if !state.context.usage_recorded`）

那段已经构造了 `RequestUsage` 并调 `update_request_usage`。把新字段填进去，并在

`check_invariants` 收到 `None` 时必须**跳过** `max_tokens_violated` 这条，
而不是当成 0 去比。

**5) 非流式路径**（`proxy.rs:862` `persist_non_stream_usage`）

这里更简单 —— 有完整的 `body: &Value`，可见文本、工具调用、usage、上游 model
全都在里面，一次解析完就能跑同一个 `check_invariants`。两点提示：

- `extract_non_stream_usage()`（`proxy.rs:805`）已经把上游 model 取出来了，

- 可见文本要从 body 里按协议取（Chat 的 `choices[].message.content`、
  Anthropic 的 `content[].text`、Gemini 的 `candidates[].content.parts[].text`），
  `adapters.rs` 里已经有各协议的字段路径可以参考。

**6) 新模块** `src-tauri/src/model_audit/mod.rs` + `invariant.rs`

**纯函数，不依赖 Tauri、不依赖 axum、不碰数据库。** 输入一个 `Observation` 结构，

## 五、阶段 P1：流式切分指纹（SCV）

### 原理

`usage` 字段是中转商可以随手改的，但**流式 SSE 的增量边界来自推理引擎本身** ——
那是真实生成模型吐 token 的边界。要伪造它得重新实现一个分词器再重切整个输出流，
成本高得多，而且会破坏首字延迟与帧间隔的规律。

所以每一个流式响应都自带一份**生成侧分词器指纹**，免费的。

### 要采的统计量

在同一个 `Delta::Text` 拦截点上顺手采（都是 O(单帧长度)）：

- `max_digit_run`：单帧内最长连续数字串。这是生成侧数字分组粒度的**上界**。
- `max_han_run`：单帧内最长连续汉字串。
- `max_space_run`：单帧内最长连续空白串。
- `median_delta_chars`：帧长度中位数。
- `ttfb_ms`：首帧到达时刻（`Instant` 差值）。

### 必须先排除帧批处理

很多中转商和 CDN 会把多个 SSE 帧攒成一个发。**不先识别这件事，所有切分统计都是废
的。** 判据：帧长度中位数显著大于典型 token 长度，或者多帧的到达时刻完全相同。

一旦判定批处理，**所有切分类结论必须降级为「不可用」**，不是「正常」。参照实现里
这是 `scv.batched` 这个前置判断，对应 `python/modelaudit/signals/stream.py`。

### 交叉检验：被动模式下到底能做到哪一步

这一节我第一版写错了，而且错得很容易误导人，所以把推理过程留在这里。

**原本的写法是**：「把 P0 拿到的计费侧粒度和 P1 拿到的生成侧粒度一对 —— 如果 `usage`
反映「13 位数字算 13 个 token」（逐位切分），而流式帧里一口气吐出 4 位连号数字
（整块切分），那么算钱的分词器和生成文本的分词器不是同一个。」

**错在哪**：被动流量里**拿不到**「13 位数字算几个 token」这个量。`prompt_tokens` 和
`completion_tokens` 都只是**总数**，没法拆出某个特定子串的贡献。要拆出来必须做**差分**
——  发两条只差那个串的请求再相减，那是主动 TDF，日常业务流量里不会恰好出现这种配对。

所以被动模式下，交叉检验分三层，前两层能做，第三层不能：

**① 硬上界（Proof 级，被动完全可做）**

每个非空文本增量帧至少携带 1 个 token，所以：

```
可见输出 token 数 ≥ 文本增量帧数
```

违反即硬证据 —— 上报的 token 数比帧数还少，说明 `usage` 不是数这段输出得来的。
反过来不成立（一帧可能带多个 token），所以**只查这一个方向**。
`text_delta_count` 这个字段就是为它准备的。

**② 整段比率的一致性（统计级，被动可做）**

输出文本代理是看得到的，`completion_tokens` 也拿得到，所以能算出这段输出的
**整段** token/字节比率，再和帧边界反映的平均切分粒度比。

> **单位必须是「字节」而不是「字符」，这一点我第一版写错了。** P0 里 `Context`
> 累积的是 `visible_output_bytes`（`String::len()`），而中文一个字占 3 字节 ——
> 按「字符」去理解那个数会直接算错 3 倍。
>
> 选字节的理由是这两条（都和分词器无关）：
>
> 1. **P0 已经记的就是字节数**，不用加字段
> 2. **和 `byte_bound` 单位统一**，少一处换算出错的机会
>
> 我原来还写了第三条理由「字节的跨语言波动比字符小三倍」。**那条是错的，已删。**
> 实测（`verify_proxy_design.py` 方案三）：哪个单位更稳**完全取决于分词器对中文的
> 覆盖度** ——
>
> | 分词器对中文的覆盖 | token/字符 英中差 | token/字节 英中差 | 哪个更稳 |
> |---|---|---|---|
> | 词组全收（Qwen / o200k 类） | 1.3× | 2.4× | 字符 |
> | 只收单字 | 2.5× | 1.2× | 字节 |
> | 完全不收（字节回退） | 7.6× | 2.5× | 字节 |
>
> 两个单位各有胜场，没有普适答案。这反过来说明下面那两条使用纪律**更有必要**：
> 波动幅度本身就随分词器变，所以这个指标天生不适合比绝对值。

比法：

- `usage` 说平均 1 token ≈ 4 字节，而帧切分显示平均 1 帧 ≈ 1.5 字节 → 不一致
- 只能单向：一帧可能带多个 token，所以**帧数 ≤ token 数**恒成立，
  只有「帧比 usage 更碎」才是矛盾

**这个指标受输出语言成分影响，所以有两条使用纪律：**

1. **不要跨渠道直接比绝对值。** 渠道 A 的用户都在写中文、渠道 B 都在写代码，
   两边的比率天然不同，那不是证据。
2. **优先在同一渠道内做时间序列自比。** 比率突然跳变才是信号 —— 这也正好接上
   P1.5 的漂移检测。要跨渠道比，得先按输出语言成分分桶。

这比逐组对比弱得多，但它零成本，而且样本量随使用增长。

**③ 逐组粒度对比（被动做不到，需要差分）**

「13 位数字算几个 token」这种针对性读数，只有两条路拿得到：下一节的**影子差分**
（用多轮对话的 prompt 增量，仍然是被动的），或者 P2 的主动 TDF。

### 三档而不是两档，这是硬要求

不管哪一层，结论必须有三档：

```rust
// ⚠ 未经 cargo check 的示意代码，字段名/借用需按实际代码调整
enum AxisResult { Contradiction, Consistent, NotComparable }
```

模型回答里恰好没有多位数字，那是「这次没法比」，不是「一致」。把它记成一致，
等于凭空发放清白证明。

## 六、阶段 P1.5：影子差分与跨渠道对比（代理独占）

这一节是代理位置的两个独占红利。工作量都不大，但第一个能补上 P1 第三层的缺口。

### 影子差分：用多轮对话拿到计费侧粒度

主动 TDF 要专门发三条请求做差分。但**多轮对话天然就是递增前缀** —— 第 N 轮的
prompt 包含第 N-1 轮的全部内容加上新增部分。而代理**知道新增的是什么文本**，
因为它就是转发者。

```
观测 = prompt_tokens(第 N 轮) − prompt_tokens(第 N-1 轮)
期望 = 本地 BPE(assistant_{N-1} + user_N)
```

两者之差应该是一个常数（每轮固定的角色标记开销）。积累几十个这样的配对做回归，
检验两件事：

- **截距**是否稳定 —— 稳定说明本地 BPE 和这个渠道的分词器一致
- **斜率**是否为 1.0 —— 这一项尤其值钱：如果中转商把 token 数系统性放大 1.2 倍，
  斜率就会是 1.2，而这是**虚报用量的直接证据**

它的性质很好：完全被动、不可能被识别成检测（它就是正常使用）、样本量随日常使用
自然增长。

### 先解决一个前提：代理怎么知道两条请求属于同一会话

这一点我第一版漏了，而它是**实施时第一个会卡住的地方**。

核实过：`proxy.rs` 里**没有任何会话概念**（grep `session_id` / `conversation` 为空），
`request_events` 表里也没有能关联两条请求的字段，只有 `provider_id` / `route` /
`created_at`。`commands/sessions.rs` 里那个 `SessionMeta` 读的是**客户端自己的会话
文件**（带 `source_path`、`resume_command`），不是代理在转发时维护的东西。

API 本身是无状态的，客户端也不会传会话 id。**但不需要引入会话 id** —— 直接用
prompt 的前缀关系配对就行：

```
对每次请求，在转发时（此时手上有 messages 原文）算两个值：
  prompt_msg_count        — 消息条数
  prompt_chain_hash       — 全部消息内容的链式 SHA256
  prompt_chain_hash_m2    — 去掉最后两条后的链式 SHA256

配对判据（第 N 次 与 第 N-1 次）：
  第N次.prompt_chain_hash_m2 == 第N-1次.prompt_chain_hash
  且 第N次.prompt_msg_count == 第N-1次.prompt_msg_count + 2
```

链式哈希就是 `h = SHA256(h_prev || role || content)` 逐条推进。`sha2` 已经在依赖里
（`Cargo.toml:30`），不用新增。

**两个实施细节，搞错了配对率会接近零：**

**① 必须在协议转换之前、基于客户端原始请求体算。** XY Switch 会做协议转换
（`adapters.rs`），客户端发 Anthropic 格式、上游可能收 OpenAI 格式。而配对要看的是
**客户端这一侧的会话连续性** —— 下一轮客户端带回来的是它自己格式的历史。在转换后
的请求体上算哈希，前后两轮根本对不上。

**② 各协议的消息容器字段名不同，不能一律当成 `messages`。** 核实过：

| 协议 | 消息容器 | system 放哪 |
|---|---|---|
| OpenAI Chat | `messages` | 数组内 `{"role":"system"}`（`adapters.rs:319`） |
| OpenAI Responses | `input` | 同上 |
| Anthropic | `messages` | **顶层 `system` 字段**（`adapters.rs:277`） |
| Gemini | **`contents`** | **顶层 `systemInstruction`**（`adapters.rs:566`） |

Anthropic 和 Gemini 的 system 在数组**外面**。只哈希数组会漏掉它 —— 而 system
恰好是最该纳入的那条（中转商改写 system prompt 时，配对失败率会跳变）。
建议的做法：把顶层 system 当成链的第 0 条先喂进去，再逐条推进数组。

这个方案有三个顺带的好处：

**① 天然处理历史截断与摘要替换。** 很多客户端会在上下文变长时截掉早期消息，或者
用一段摘要替代。那种情况下前缀关系不成立，判据**自动不匹配、自动跳过** ——
不需要额外写检测逻辑，也不会用错配的数据算出假结论。

**② 不存原文，只存哈希。** 符合第八节的隐私原则：代理看得到一切，但只留下结构。

**③ 顺带能发现 system prompt 被改写。** 如果中转商在转发时重写了 system prompt，
那么下一轮客户端带回来的历史就和代理记下的哈希对不上 —— 配对失败率异常高本身
就是个信号（虽然弱，因为客户端自己截断也会这样）。

> **这三条都跑过了。** `verify_proxy_design.py` 方案一共 22 项验证全部通过：
> 连续 5 轮配对成功、隔轮不误配、历史截断自动跳过、摘要替代自动跳过、
> **条数相同但历史内容被改仍然配对失败**（说明判据不只靠条数）、system 被改写
> 配对失败而条数不变、Anthropic 顶层 system 当第 0 条配对成功、Gemini 的
> `contents` + `systemInstruction` 同样成功、落库的三个值里不含任何原文。
>
> 其中一项特别值得记：**漏掉顶层 system 时配对照样成功**，所以这个错误不会立刻
> 暴露 —— 它只是让你永远检测不到 system 被改写。验证脚本里专门对比了这两种实现。

**实现时别纠结条数判据该用 `==` 还是 `>=`：哈希决定一切，条数只是廉价的前置筛选。**
验证里把 `== +2` 换成 `>= +2`，所有断言照样通过；只比哈希、完全不比条数，也照样
正确配对、照样挡得住被改过的历史。条数检查不提供额外安全性，它的价值是先过滤掉
绝大多数不可能的配对，省下比较 64 字节哈希的开销。

**但有一类轮次会一次加超过两条消息：带工具调用的。** 典型序列是
`assistant(tool_calls)` + `tool_result` + `user_N`，一轮加 3 条（多个工具就更多）。
所以 `== +2` 配不上它们 —— 这**和「要剔掉工具调用轮」正好一致，不是问题**。
但如果你想用「配对失败率」当信号（发现 system 被改写），就必须先把工具调用轮排除，
否则失败率会被它们污染成噪声。

要新增的字段：

```rust
// ⚠ 未经 cargo check 的示意代码，字段名/借用需按实际代码调整
("prompt_msg_count",     "INTEGER"),
("prompt_chain_hash",    "TEXT"),
("prompt_chain_hash_m2", "TEXT"),
```

**所以影子差分的工作量不小**：三个字段 + 请求路径上算哈希 + 配对查询 + 回归统计，
再加上它依赖 P2 的 BPE 引擎。别被「只是做个差分」骗了。

**还有三处必须先处理，否则结论是错的：**

**① prompt caching 会让语义变掉。** `cached_tokens` 单独计费时 `prompt_tokens` 的
含义就不是「这轮 prompt 有多少 token」了。必须把有 cache 命中的轮次**剔掉或单独
建模** —— `request_events` 已经有 `cache_read_tokens` / `cache_creation_tokens`
两个字段，拿它们当筛选条件。

**② 它依赖本地 BPE，也就是依赖 P2 的分词器引擎。** 所以 P1.5 的这一半在实现顺序上
挂在 P2 后面，或者至少要先有一个能读 `tokenizer.json` 的最小实现。

**③ 新增内容是用户聊什么就是什么**，不像主动 TDF 那 11 组被测串是精心挑的、
能针对性暴露分词器差异。判别力因此弱一些，靠样本量补。

> **这个想法我没有实现和验证过。** 它在参照实现里也不存在 —— 那套是客户端视角的，
> 拿不到多轮上下文。所以它是设计思路，下面三件事我还没想清楚：
>
> * **「角色标记开销是常数」这个假设本身需要验证。** 不同协议、不同模型的 chat
>   模板不一样，而且有些模型在带工具调用的轮次会插入额外标记。截距稳不稳是个
>   实证问题，不是推理结论。
> * **工具调用轮次怎么算。** assistant 消息里含 `tool_calls` 结构时，「新增内容的
>   token 数」不是简单地对文本做 BPE —— 函数名和 JSON 参数的序列化方式会影响结果。
>   最稳妥是先把带工具调用的轮次也剔掉。
> * **多少样本才够。** 我没有定量门槛。建议先收几十对、看截距的标准差收不收敛，
>   再决定要不要据此下结论。
>
> 先用少量真实会话验证截距稳不稳，再决定要不要铺开。

### 这个方案跑过了 —— 验证结果与四条实施门槛

写完上面那段之后我把方案实际跑了一遍：
`E:\claude project\model-audit-framework\python\verify_proxy_design.py`
（51 项验证，用合成分词器 + 模拟的上游计费行为）。结论是方案成立，而且得到了
上面那三个「没想清楚」里缺的定量答案：

**① 诚实渠道下斜率与截距都收敛得很干净。** 40 轮对话、39 对样本：
斜率 `1.0000`、截距 `8.00`（恰好等于 2×每轮角色开销）、残差标准差 `0.000`。
分词的确定性在这里体现得很彻底。

**② 虚报系数能被直接读出来。** 注入 1.1 / 1.2 / 1.5 / 2.0 倍虚报，拟合斜率分别
是 `1.1000 / 1.1996 / 1.4997 / 2.0000`，偏差都在千分位以下。**斜率就是虚报倍数**，
这条站得住。

**③ 只需 3 对样本就能把 1.2 倍虚报和诚实分开 —— 但这有前提。**

「3 对」是在**残差精确为 0** 的条件下得到的，而残差为 0 是因为模拟里 `prompt_tokens`
就是精确的 BPE 和。真实上游会有抖动（chat 模板开销随轮次微变、特殊 token、空白处理
差异），残差不会是 0。加噪声重测：

| 注入噪声 SD | 实际残差 SD | 最少样本对数 |
|---|---|---|
| 0 | 0.00 | 3 |
| 1 | 1.78 | 3 |
| 3 | 5.21 | 3 |
| 10 | 17.12 | 6 |

残差放大 17 倍，样本需求只从 3 涨到 6 —— **比预想的鲁棒**。所以不需要几十对。

**实施时的判断方法：看残差标准差。** 它直接指示样本够不够 —— 残差接近 0 就几对即可，
残差到十几就收十来对再下结论。不要用固定的样本量门槛。

**④ 但有一个容易踩的坑：自变量的方差决定斜率精度。**

回归的自变量 x 是「新增内容的 token 数」。如果用户的使用模式让每轮新增长度都差不多
（比如固定模板的自动化调用），杠杆就极小，舍入噪声会被放大：

| 对话形态 | x 标准差 | 唯一值个数 | 虚报 1.2× 的斜率偏差 |
|---|---|---|---|
| 长度差异大（真实对话） | 110.6 | 27 | **0.0004** |
| 长度几乎不变（固定模板） | 0.8 | 3 | 0.0084 |

精度差一个数量级，但两者都远小于 0.2 的信号 —— **所以依然可用**。实施时加一条
前置检查就行：**x 的取值范围过窄（比如唯一值少于 5 个）时，标注「杠杆不足、
斜率精度下降」，而不是照常下结论。**

验证也确认了那三条前提都是必要的，而且后两条的破坏方式不一样：

- **prompt caching 不剔除**：残差标准差从 `0.000` 爆到 `1252.994`，斜率跑到 `1.79`。
  剔掉受影响的配对后恢复 `1.0000`。
- **工具调用轮不剔除**：残差到 `27.6`。注意这里有个细节 —— 破坏来源**不是**「可见
  文本为空」，而是「上游对 `tool_calls` 的 JSON 计费、而本地 BPE 只看 `content`」，
  两边不同步。我第一版测试把 content 清空，结果上游计费和本地期望同步减少、
  残差纹丝不动，等于什么也没测到。
- **角色开销不恒定**：残差到 `83.6`，但**斜率仍是 `0.9718`** —— 所以
  「虚报检测」比「截距标定」鲁棒得多。截距不稳时不要放弃斜率。

> 仍然要说清楚：这些数字来自**合成分词器与模拟的上游计费**。真实中转商的 chat
> 模板开销、cache 策略、工具调用计费方式都可能不同，所以 XY Switch 实现之后
> 仍需用真实会话复核一遍截距稳定性。方案的**结构**验证过了，**参数**没有。

### 跨渠道对比是免费的

反正多个渠道都要转发，拿它们互相比就是免费的 peer 基线。它还能回答单渠道审计
回答不了的问题：**两个渠道背后是不是同一个上游**（切分行为与错误形状完全一致
往往说明是）。

### 行为漂移检测

昨天 13 位数字算 5 个 token、今天算 13 个，这是上游换了。单次审计永远发现不了
「从某个时刻起开始掺水」，而代理天然能发现 —— 这是免费的 self-history 基线，
而且比它更强。

顺着这条线还有一个我那套框架完全碰不到的信号：**高并发时行为是否变化**。如果某渠道
在高峰期切分粒度和延迟分布都变了，很可能它在高峰期切到了便宜模型。

这两项都是纯 SQL 聚合，不需要新的采集字段。

## 七、阶段 P2：参照库与概率定位

到这一步才需要「参照物」—— 也就是「gpt-4o 的分词器应该给出什么读数」。

### 参照从哪来：不要内置任何答案表

参照实现里这一条是刻意的：**不内置任何「cl100k 下这个串应该是 N 个 token」的数字
表**。那种数字无法在离线环境核实，硬编码进来就是编造，而且模型换版本整张表就全错。

两条获取路径，第一条不花钱：

**① 从官方分词器文件本机现算。** 用户下载各家公开的分词器（OpenAI 的 `.tiktoken`、
HuggingFace 的 `tokenizer.json`），程序用零依赖 BPE 实现算出参照值。数字来自用户
自己下载的真实文件，指纹里记 SHA256 可逐字节复核。参照实现见
`python/modelaudit/tokenizers.py`（BPE + 两种格式 + 手写预分词器）和
`python/modelaudit/refgen.py`（生成指纹 + 与实测对账）。

**② 用官方直连 key 实测。** 最强（权重 1.00），但要花钱、要有每家的 key。
Claude / Gemini 不公开分词器，只能走这条。

### Rust 侧移植的两个注意点

**预分词不能用正则。** 各家的切分正则含 `\p{L}` `\p{Lu}` 这类 Unicode 属性类。
Python 的 `re` 不支持，所以参照实现是**按公开正则手工实现了等价状态机**，字符分类
走 `unicodedata.category()`。

Rust 侧的等价物是 `unicode-properties` 或 `unicode-general-category` crate ——
这会**新增一个依赖**，需要你权衡。标准库的 `char::is_alphabetic()` 等方法是近似的，
对 `\p{L}` 够用，但 `\p{Lu}`/`\p{Lt}`/`\p{Lm}`/`\p{Lo}` 的细分（o200k 的驼峰分支
要用）标准库给不出来。

**BPE 计数不要放在转发路径上。** 11 组 × 3 级的 BPE 在 Python 下要几十毫秒，Rust 快
很多但仍然不该放在热路径 —— 代理慢一点用户立刻能感觉到。放到用户主动触发的离线
分析里。

### 概率排名：那一档「库外」是整个设计的要害

输出形式是候选后验概率排名：

```
候选                            概率     可比/一致
gpt-4o                        45.1%      11/11
gpt-4o-mini                   45.1%      11/11
（库外：不是库里任何一个）         9.7%          —
qwen2.5-72b                    0.0%       3/11
```

**那一档「库外」不是摆设，它是最要紧的一项。** 库里一个都对不上的时候它必须排第一 ——
否则归一化会把概率全分给库内候选，于是「库里没有一个对得上」会被显示成「最不像的
那个占 100%」。

这个坑我真实踩过。第一版库外似然按「n 组全部偶然撞上」算（`p_coincide^11`），低到
任何 9/11 匹配的候选都能压倒它，结果库外模型被指认成了 `gamma 97%`。

**正确形状是** `L_outside = p_hit^n × outside_edge`：分词是确定性过程，真模型**应该
全组匹配**，所以最佳候选只要存在任何一组失配，库外就反超。`outside_edge` 必须落在
`((1-p_hit)/p_hit, 1)` 区间内 —— 小于下界库外永远赢不了，大于 1 则永远赢。
参数校验必须挡住退化配置。

### 定位能力的硬上限

必须让用户看到这条，否则会产生错误的确信：

| 观测 | 能得出什么 | 强度 |
|---|---|---|
| 分词器逐组读数**不一致** | **不是这个模型** | 强。分词确定性，差分已消掉 chat 模板开销 |
| 分词器逐组读数**全一致** | 在这个**词表等价类**里 | 弱。同厂同代大小号往往共用词表 |

即便只命中一个候选，也**不能写成「就是它」** —— 库的覆盖面有限，真实模型完全可能是
另一个共用该词表、但没被采进库的型号。库里只有 `gpt-4o` 而渠道在跑 `gpt-4o-mini`
时，写「指向 gpt-4o」就是一句错误指认。

## 八、数据与隐私：只留结构，不留内容

代理看得到一切，所以必须明确只留下什么。这既是隐私考虑，也让归档体积可控。

**存**：usage 的几个数、上游自报 model、可见输出字节数、文本增量帧数、切分统计量
（三个 run 的最大值、帧长中位数）、帧到达时刻偏移、响应头的**名字**、命中的证据 id。

**不存**：请求正文、响应正文、响应头的**值**（凭据类头部尤其）、工具调用的具体参数。

需要字符分布信息时，存**直方图**而不是原文 —— 比如「这次请求里数字字符占 12%、
汉字占 40%」，足够做回归，但还原不出内容。

> 参照实现里 `runner.redact_secret()` 会把 API key 从响应体和错误串里抹掉，
> 并且凭据类响应头**保留名字、清空值**（因为协议指纹只需要头名字）。
> XY Switch 已经走 Windows 凭据管理器，这部分继承现有做法就行。

## 九、三条不能丢的诚实性约束

这三条在代理场景下**风险比客户端更大**，因为代理 24/7 跑着，会积累大量「看起来统计
显著」的发现。

### ①「未测到」必须和「没问题」严格分开

代理早期样本不足，这时候只能判「未测到」。每个关切都要有最小样本量门槛，没到门槛
就是**没查**，不是查了没事。

市面上多数「中转商测评」栽在这里：跑几个提示词、看着像那个模型、宣布渠道可靠。
参照实现里为此专门设了一个 `Untested` 档位，并且在判定分支里把
`scored_count == 0` 排在**所有统计档位之前** —— 一条可打分证据都没有时，不管先验
是多少，结论只能是「没测」。

### ② 分族软封顶不能省

同一个分词器失配会让 11 个分词组**一起**失配。直接加和会让后验变成 0.9999 ——
但那 11 条证据背后只有**一个**独立事实。这叫独立性谬误，而且它是单向的：只会制造
假指控，不会制造假清白。

**单条证据封顶解决不了这个问题。** 实测数据（参照实现里的数字）：

```
10 条各 +2.0 nats
  不封顶      : 20.0 nats → 后验 1.000000   ← 荒谬
  仅单条封顶  : 20.0 nats → 后验 1.000000   ← 毫无作用
  加族软封顶  :  3.0 nats → 后验 0.7325     ← 合理
```

必须按证据族做 `c * tanh(sum / c)`。样本量越大这个坑越深，代理尤其要小心。

### ③ 不要在 UI 上显示「渠道可信度 87 分」

代理做成仪表盘太自然了，但那种数字会被当成客观事实。后验概率**不是**「这个渠道有
问题的真实概率」，而是「在这套先验和似然模型下，证据把信念推到了哪里」。

一个分数会把三件完全不同的事压成一个数：有硬证据、有统计迹象、以及**压根没测到**。
压完之后用户无从分辨，而第三种情况最常见。

### 界面上该显示什么

正面说一下建议的产品形态 —— 这是用户最终看到的东西，也是整件事的落点。

**实时只弹硬证据。** P0 的四条是 Proof 级，不依赖先验和权重，可以直接告警：

```
⛔ 渠道「某中转」上报的输出 token 数（1240）超过了输出文本的字节数（890）
   一个 token 至少解码出 1 字节，所以这在数学上不可能。
   已扣除：上报的推理 token (0)、工具调用字节 (0)、特殊 token 余量 (4)
```

把**已扣除了什么**写出来很重要。它让用户能自己判断这条结论可不可信，也让「是不是
误报」这个问题有据可查。

**日常状态用计数，不用评分。** 「近 200 次请求中 3 次命中硬证据」比「可信度 87 分」
诚实得多，而且用户知道该怎么理解它。

**模型身份用三档并列。** 见上面第三节。

**定位结果用概率排名 + 库外档**，并标明「这是相对库内候选的概率，不是客观概率」。

**「未测到」要有独立的视觉呈现**，和「未发现问题」用不同颜色、不同措辞，并且一律
附一句「这不等于没问题」。参照实现里这两档在 HTML 报告里是两个不同的 CSS 类，
而且有一条回归测试专门确认它们不相同 —— 听起来小题大做，但市面上多数「中转商测评」
恰恰栽在这里。

落到 XY Switch 的设计语言上（见第三节「前端现状与约束」）：

| 档位 | 建议的呈现 | token |
|---|---|---|
| 已证实（硬证据） | `status-pill` + `XCircle`，实色 | `--xy-danger` |
| 存疑 / 有弱信号 | `status-pill` + `AlertTriangle`，柔色 | `--xy-warning-soft` |
| 未发现问题 | `status-pill` + `CheckCircle2` | `--xy-success` |
| **未测到** | **描边而非填充**，灰度，文案带「未查」 | `--xy-border-strong` + 次级文字色 |

关键是**「未测到」不要用绿色系**。它和「未发现问题」只要同色系，用户就会读成
「没事」—— 而这恰好是整份文档反复强调的那个失败模式。用灰度 + 描边，视觉上
明确表达「这里是空的」而不是「这里是好的」。

**统计类结论必须用户主动点「分析」才算**，报告里要带上「这条结论还没排除什么」。

## 十、踩坑清单（都是我真实踩过的）

**TDF 阶梯三级必须共用同一个填充串，两级追加的片段必须完全一致（都带分隔符）。**
Rust 版我两处都写错过，后果是上限 7.0 的最强信号对诚实渠道也整族失效 —— 而且失效
方向是**静默的**，报告看起来一切正常。如果 P2 要做主动 TDF，这条必须用回归测试钉死
（参照 `python/modelaudit/preflight.py:268` 的 `c_tdf_ladder` —— 它比对阶梯文本的
前缀关系，是真跑过的那一份；Rust 骨架里同名的
`plan.rs::tdf_rungs_share_one_filler_and_append_the_same_fragment` **从未编译过**，
别拿它当参照）。

**被测串的字符数必须现算，不能手写常量。** 我手写的 11 组错了 4 组（泰文漏算组合符
10→20、emoji 漏算 ZWJ 与肤色修饰 12→15、代码片段 24→28、常见汉字 17→16），
而它是「每字 token 数」这类观测量的分母。

**稳定性判据必须是 `d2.is_some() && d2 == Some(d1)`。** 写成「d2 没采到就当它稳定」，
一次 HTTP 429 就能造出一条凭空的失配指控。

**HTTP 客户端必须显式设 User-Agent。** 这条你已经遇到过了：urllib 不设会发
`Python-urllib/3.x`，被 Cloudflare 直接拦成全部 403。**reqwest 的默认 UA 同样可能被
拦** —— `proxy.rs` 转发时如果没显式设 UA，建议加一个可配置项，并在诊断里试探。

**协议探针故意发非法请求，它的 4xx 是信号本身不是失败。** 算成功率时必须把这类请求
排除，否则诚实渠道会被判成「采集失败」。对 XY Switch 而言对应的是：**健康检查和
业务请求要分开统计**，`request_events` 已有 `affects_health` 字段，别把它们混在一个
成功率里。

**采集大面积失败必须让结论作废，而且要说在最前面。** 埋在「运行汇总 ok=0」里会直接
误导人 —— 尤其旁边还写着「http_error 正常」的时候。

**改判据后要搜一遍相关文案。** 我给参照库加了一个新的权威性档位，却忘改
`library list` 的提示文案，结果用户刚建好 2 条有效指纹却被告知「官方直连 0 条，
只有官方直连才有权威性」。

**Windows 批处理里不要放中文。** 和本项目无关但值得记：cmd 在 `chcp 65001` 下按块
读 `.bat` 会把多字节 UTF-8 从中间切开，半行 `echo` 被当成命令执行。

## 十一、怎么验证

### 分层策略

把检测逻辑放在**不依赖 Tauri、不依赖 axum、不碰数据库**的纯函数模块里
（`src-tauri/src/model_audit/`），这样：

```bash
cargo test --manifest-path src-tauri/Cargo.toml model_audit
```

就能跑，不用起代理、不用连网、不用 GUI。这是我上一轮最有价值的一条教训 —— 参照
实现里把业务逻辑抽进 `session.py`（不依赖 tkinter），结果即使在没有 tkinter 的
环境里也能验证 49 项，GUI 只剩一层薄绑定。

### 用假上游做端到端

参照实现里有一个 `mock.py`（496 行）：**一个可按开关植入故障的真 HTTP 服务**，
让审计走真正的传输层和真正的 SSE 解析，而不是在内存里自己骗自己。它的故障开关包括

- **植入故障必须被抓到**（无漏检）
- **诚实渠道必须零告警**（无假阳性）

第二类比第一类重要。

## 十二、不要做什么

**不要先做主动探针。** 它受「考试作弊」影响，而被动部分不受。先把免费且不可规避的
拿到手。

**不要在转发路径上做 BPE 或任何重计算。** 代理变慢用户立刻能感觉到。

**不要改透传行为。** 上游自报的 model 要记录，但给客户端的响应保持原样 —— 改了会
破坏客户端兼容性。

**不要把「存疑」当结论推给用户。** 后验 0.6~0.9 的意思是「值得继续查」。要在 UI 上
给出强结论，只用 Proof 级，并且把那条硬证据的推导过程完整展示出来。

**不要让「未发现问题」看起来像背书。** 它只覆盖框架测到的那几项，而且基线缺失时
几乎没有含金量。

## 附：建议的实施顺序与工作量感觉

| 阶段 | 内容 | 相对工作量 | 产出 |
|---|---|---|---|
| **P0-** | **上游自报 model 并排显示** | **很小 —— 1 个字段 + 2 处回填 + 1 列 UI** | **立刻能看到「真实模型是谁」** |
| P0 | 被动不变量（四条硬证据） | 小 —— 7 个字段 + 一个纯函数模块 + 三处挂钩 | Proof 级结论，零成本不可规避 |
| P1 | 流式切分指纹 + 交叉检验 | 中 —— 在已有逐帧循环里加统计 | 不需要参照库的模型身份线索 |
| P1.5a | 跨渠道 / 跨时间对比（第六节） | 小 —— 纯 SQL 聚合，不需要新字段 | 免费的 peer 与 self-history 基线 |
| P1.5b | 影子差分（第六节） | **中** —— 3 个字段 + 协议前算哈希 + 配对查询 + 回归；且依赖 P2 的 BPE | 被动拿到计费侧粒度与虚报系数 |
| P2 | 参照库与概率定位 | 大 —— BPE 引擎 + 预分词 + 概率模型 | 定位到词表等价类 |

**先做 P0-**（第三节）。它半天能完，而且直接回答你要的那个问题 —— 用户立刻能在
用量列表里看到「请求的是 gpt-4o，上游自报的是什么」。信息本来就在数据库里，
只是从没并排显示过。

如果之后只做三件，我会选 **P0 + P1 + P1.5a** —— 这三件都不需要发任何探针，也就都不受
「考试作弊」影响，而且全部是 XY Switch 处在转发位置上才拿得到的东西。P2 能回答
「它是谁」，但那是锦上添花；前三件回答的是「它在骗你吗」，那个更实在。
